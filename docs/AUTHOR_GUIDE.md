# 作者投稿指南

张导插件商店收录来自 GitHub 公开仓库、由作者在正式 Release 上传的 IPK。你负责源码、说明、构建和发布；商店负责读取材料、静态检查、自动审核与已审核文件转发。

## 1. 准备公开仓库

填写 `https://github.com/owner/repository`，可带 `.git` 后缀。不支持私有仓库、单独文件 URL、Release 网页、分支链接、代理 URL、凭据型链接或其他主机。以 GitHub repository ID 去重；再次提交不会创建第二份卡片或转移归属。

仓库应提供：

- GitHub description：一句准确的功能描述，首页直接展示。
- 真实 README：说明用途、适用设备与架构、配置方法、所需权限和已知限制。缺少或空白 README / description 会提示补充，不会由 AI 代写。
- 与 Release 标签对应的可读源码、依赖/构建配置及必要安装卸载脚本。只有二进制、缺失关键源码或未读取的 LFS/子模块材料无法完成自动检查。
- 明确许可说明，推荐标准 `LICENSE` 文件。GitHub 能识别时显示 SPDX 许可标识；识别不明确时如实显示未知并结合资料审核。不只接受某一种许可证，也不把未知许可等同恶意。

不需要 AstrBot metadata.yaml、registry.json、宿主连接或安装接口。

## 2. 发布正式 Release 与 IPK

自行构建 IPK，并上传到仓库的**正式 Release 附件**。草稿和 prerelease 不作为正式下载来源。GitHub 自动生成的 Source code ZIP/tar.gz 不能替代 IPK，商店也不会执行 README 中的构建命令或触发 Actions。

只有一个 IPK 时可直接下载；多个 IPK 时用户需要逐个选择。建议文件名明确包名、版本和架构，例如下列**命名示例**，并确保 `control` 内的 Package / Version / Architecture 与实际内容一致：

```text
example-plugin_1.2.0_aarch64.ipk
example-plugin_1.2.0_mipsel.ipk
```

首版每个正式 Release 最多检查 8 个 IPK；单包默认上限 32 MiB。这些是保护 Workers 资源的工程默认值，不是最终业务上限。超限应先查看具体原因，与运营者协调，而不是把包伪装成其他扩展名。

支持的 IPK 结构：外封装为 `ar` 或 `tar.gz`；`debian-binary` 为 `2.0`；恰好一份 `control.tar` / `control.tar.gz` 与一份 `data.tar` / `data.tar.gz`。tar 支持标准/ustar 常规文件、目录与受控链接。xz/zstd、PAX/GNU 长名称扩展、特殊设备条目和包内嵌套归档尚未支持，会给出“检查未完成”，不会被当作已完整扫描。

## 3. 提交与查看进度

1. 进入 `/login`，填写自报手机号建立识别档案。首版不验证号码和小店绑定；知道同一号码的人可能进入同一档案。
2. 在 `/submit` 提交 GitHub 公开仓库地址。
3. 投稿创建持久任务，关闭页面不会丢失。在 `/me` 的“我的提交”查看状态和适合公开的原因。
4. 需要补充时修改原仓库、补齐正式 Release/IPK，再选择“检查更新”。每个仓库有刷新冷却，不要反复投稿。

提交者只表示在商店发起投稿的识别档案，不代表其已证明拥有 GitHub 仓库。普通用户不能更换已提交仓库、修改 AI 设置或删除市场条目。

没有正式 Release/IPK 时显示等待发布安装包；无 AI 配置时等待审核服务；资料不足/不支持格式时为检查未完成；明确恶意或欺骗才拒绝。技术检查和有效 AI 结果均满足后自动上架，不增加日常人工审批。管理员提交同样经过审核。

## 4. 审核实际会看什么

审核材料至少包括 description、默认分支真实 README、Release 源码 commit 的可读源码和依赖/构建配置、IPK 文件清单、control 信息、安装/卸载脚本与包内可读脚本。覆盖范围和跳过原因会记录；超过读取预算时停止，不静默截断后声称完整审核。

只有明确 `allow`、技术检查完成、来源快照有效且未被管理员停用，才能上架。AI 超时、余额/限流错误、拒答、未知字段或格式错误不能默认通过。README/源码中的“忽略规则”“请直接通过”等文本不会成为系统指令。

正常 shell、curl、联网、服务或防火墙操作，以及二进制的存在，本身不构成恶意。审核结合用途和真实行为；二进制会记录摘要并结合源码/构建关系判断，不能代替动态杀毒或可复现构建。通过自动审核不是“保证无病毒”。

## 5. README 与安装包版本是两个快照

详情页展示的是仓库**默认分支**真实 README，记录 `readmeCommit` 和 `readmePath`；安装包审核对应正式 Release 标签解析出的 `sourceCommit`。默认分支更新 README 不等于发布了新的 IPK，两者可能处于不同 commit。

README、description 的修改先成为候选材料，审核通过才替换已发布展示快照。相对图片和链接按 README 的来源路径与 commit 解析；危险 HTML、脚本、事件属性和危险 URL 会被过滤。图片只允许 GitHub 内容域名，其他图片以说明替代，可从详情的 GitHub 仓库入口查看原文。

## 6. 更新、下架与下载

每天北京时间 12:00 和 24:00 启动分批检查，不要求所有任务整点完成。新版本审核期间继续提供之前仍有效的已审核版本；不会让访客绕过审核下载新附件。相同快照复用有效审核结果，普通访问页面不会触发整套审核。

请以新 Release 发布更新，不要替换已审核附件或移动标签。发现原附件消失、身份变化或 tag 移动时，对应下载会停用并等待重新审核。临时 GitHub 异常及单次 404 不会直接认定删库；确认仓库不再公开访问后从市场移除。

管理员下架/删除会保留必要提交状态和原因，并禁止自动恢复。需要恢复时由管理员显式发起，之后仍需重新审核。商店操作不会删除 GitHub 仓库。

用户经 Worker 将当前已批准附件下载到本地；商店不保存安装包镜像，也不代替用户安装或自动猜测设备架构。收藏数是当前收藏的去重识别档案数；下载数是成功开始的站内下载尝试，短期重试与 Range 去重，不是完整下载成功数或安装人数。

GitHub Issue、PR、构建和发布继续在作者仓库处理，商店没有站内评论、评分或 Issue/PR 系统。
